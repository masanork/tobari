**Tobariプロジェクトにおけるハイブリッド暗号・署名実装の実証評価**

## 1. はじめに

本報告書は、「住民票の写し等の電子交付」の概念実証（Tobariプロジェクト）において、将来の脅威である量子コンピュータによる暗号解読（CRQC: Cryptographically Relevant Quantum Computer）を見据え、耐量子計算機暗号（PQC: Post-Quantum Cryptography）を適用した場合の影響を評価した技術報告である。

主要な検証項目である「真正性」や「転々流通防止」については別紙「住民票の写し等の電子交付にかかる技術検証報告書」に譲り、本稿ではPQC導入に伴うデータサイズ、処理性能、および社会実装に向けた実現可能性に焦点を当てる。

## 2. 耐量子暗号（PQC）導入のアプローチ

### 2.1. ハイブリッド方式の採用

現在、NIST（米国国立標準技術研究所）によるPQC標準化プロセスが完了し、FIPS 203 (ML-KEM), FIPS 204 (ML-DSA) 等の規格が確定している。しかし、これらの新しいアルゴリズムは運用実績が浅く、未知の脆弱性が発見されるリスクも否定できない。
そのため、本検証では既存の楕円曲線暗号（ECC）とPQCを併用する **「ハイブリッド方式」** を採用した。

*   **ハイブリッド署名**: 従来の署名（ECDSA）とPQC署名（ML-DSA）の両方が有効である場合のみ「正当」とみなす。どちらか一方の暗号が破られても、もう一方が安全であれば偽造を防ぐことができる。
*   **ハイブリッド鍵交換**: 共通鍵を共有する際、ECDHとML-KEMの両方で鍵共有を行い、それらを合成（KDF）して暗号化鍵を生成する。これにより、将来的に過去の通信が解読される「Harvest Now, Decrypt Later」攻撃を防ぐ。

### 2.2. 暗号学的敏捷性 (Crypto Agility)

本システムは「自己完結型ビューアー（Self-Contained Viewer）」モデルを採用している。検証ロジック（WASM）そのものがデータに内包されて配布されるため、将来的に暗号アルゴリズムの危殆化が進んだ場合でも、**「新しいアルゴリズムに対応した検証コードを含む新しいビューアー」** を配布するだけで、受信者（Verifier）側のシステム大規模改修を待つことなく、迅速な新暗号への移行が可能である。

## 3. 実装した暗号構成

本概念実証（Tobari PoC）では、以下の構成でハイブリッド暗号化・署名を実装した。

| 用途 | Algorithm ID | 構成技術 | 役割 |
| :--- | :--- | :--- | :--- |
| **発行者署名** | `ES384` + `ML-DSA-65` | **ECDSA P-384** (SHA-384)<br/>**ML-DSA-65** (Dilithium3) | juminhyo.html の発行元認証<br/>(Issuer Authority) |
| **端末所持認証** | `ES256` + `ML-DSA-65` | **ECDSA P-256** (SHA-256)<br/>**ML-DSA-65** | 転々流通防止 (Device Binding)<br/>スマートフォン内での鍵生成 |
| **経路外暗号化** | `HPKE-Base` | **DHKEM(P-256, HKDF-SHA256)**<br/>**ML-KEM-768** (Kyber768) | データ閲覧権限の制御<br/>(Passkey保有者のみ復号可能) |

## 4. 影響評価

PQCアルゴリズムは、従来の楕円曲線暗号と比較して鍵長や署名長が大きく、計算コストも高い傾向にある。これらがWebベースの電子交付において実用上の障害とならないかを確認するため、定量的評価を行った。

### 4.1. 検証ロジック（WebAssembly）のサイズ影響

ブラウザ上で動作する検証モジュール（Rust製WASM）について、アルゴリズム追加によるサイズ変化を測定した。

| ビルド | 構成 | サイズ (WASM) | 増分 |
| :--- | :--- | :--- | :--- |
| **core** | 古典暗号のみ（P-256/HPKE等） | **141,508 bytes** | - |
| **dsa** | core + ML-DSA-65 | **242,403 bytes** | +100,895 bytes |
| **full** | dsa + ML-KEM-768 | **293,103 bytes** | +151,595 bytes (累計) |

耐量子署名（ML-DSA）の追加により約100KB、耐量子鍵交換（ML-KEM）の追加によりさらに約50KBのサイズ増となった。これは格子暗号に必要な行列演算ロジックや定数テーブルが含まれるためである。ただし、Gzip圧縮後の転送量としては数10KB程度の増加であり、ブロードバンド環境下では無視できるレベルである。

### 4.2. 生成物（証明書ファイル）サイズへの影響

#### (1) ペイロードレベルでの増加
証明書データそのもの（COSE/CBOR）へのオーバーヘッドは以下の通りである。

| 適用技術 | ファイルサイズへの影響 (概算) | 備考 |
| :--- | :--- | :--- |
| **PQC署名 (Issuer)** | +3.3 KB | ML-DSA-65 署名値およびヘッダー |
| **PQC署名 (Device)** | +2.0 KB | ML-DSA-65 公開鍵 (DeviceKeyInfo) |
| **PQC暗号化 (Encrypt)** | +1.5 KB | ML-KEM-768 暗号文 (Hybrid) |
| **フルPQC構成** | **+6.8 KB** | 全て適用した場合 |

#### (2) 配布ファイル（HTML）全体での比較
WASMやUIリソースを含めた最終的な配布ファイル（HTML）での比較結果は以下の通り。

| 生成モード | .cose (データ部) | .html (全体) | 備考 |
| :--- | :--- | ---: | :--- |
| **core** (PQCなし) | 4,096 bytes | 275,000 bytes | Gzip時: 約138KB |
| **full** (PQCあり) | 5,632 bytes | 425,000 bytes | Gzip時: 約162KB |

HTML全体のサイズ（約275KB〜425KB）に対し、PQC適用によるGzip圧縮後の転送量増加は **約24KB (+17%)** 程度である。これは、Webアプリケーションとしては極めて軽量な部類に入り、UXを損なう要因にはならない。

### 4.3. 処理性能（ブラウザ実測値）

Apple M3チップ搭載機における処理時間は以下の通り。格子の計算コストは高いものの、ミリ秒単位での完了しており、人間が知覚できる遅延は発生しない。

| 処理 | 平均時間 |
| :--- | ---: |
| ML-DSA sign | 2.05 ms |
| ML-DSA verify | 0.25 ms |
| HPKE encrypt (hybrid) | 0.77 ms |
| HPKE decrypt (hybrid) | 0.31 ms |

### 4.4. エコシステム各層におけるPQC対応の見通し

PQCへの移行は一斉に行われるものではなく、各レイヤーの技術的制約によって進行速度が異なる。本概念実証の結果、ソフトウェア（WebAssembly）で実装可能な領域については即座に対応可能であることが確認されたが、ハードウェア依存領域は長期的な移行期間を要する。

#### (1) Webブラウザ (Web Cryptography API)
*   **見通し: 早い (〜2027年)**
*   W3Cおよびブラウザベンダー（Google, Apple, Mozilla）は、NIST標準化に伴いネイティブAPIの実装を進めると予想される。
*   **Gap対応**: 本PoCで実証したように、ネイティブ実装を待たずとも **WebAssembly (WASM)** によるポリフィルを用いることで、現在からでもブラウザ上で高速なPQC処理が可能である。

#### (2) スマートフォン / FIDO認証器 (Passkey)
*   **見通し: 中期 (2027年〜2030年代)**
*   秘密鍵を保護するSecure EnclaveやTPM等のハードウェア・チップレベルでの改修が必要となる。
*   端末の買い替えサイクル（3〜5年）に依存するため、PQC対応デバイスが市場の過半数を占めるには時間を要する。

#### (3) IC身分証 (Identity Smart Cards)
*   **見通し: 段階的 (Issuer先行: 〜2030年 / Full: 2030年代後半〜)**
*   **Phase A (Issuer署名)**: カード内部の秘密鍵演算（チップ認証等）は既存のRSA/ECCを維持しつつ、券面事項データ（DG1等）への**発行者署名（SOD）にML-DSAを採用する**ことは比較的早期に可能。
    *   **Gap対応（クローニング対策）**: 現行チップでも実装可能な**共通鍵暗号（AES/SHA）を用いたサーバーサイド認証（Online Symmetric Auth）**を併用することで、チップ自体の真正性も実質的に担保可能である。これは、カード固有鍵で生成したMAC（Message Authentication Code）をオンラインでIssuerに送信して検証する方式で、新しいチップの配布を待たずに導入できる現実解である。
*   **Phase B (Chip演算)**: カード内部でML-DSA/ML-KEMを計算する（Active Authentication / Terminal Authentication）には、チップ性能と通信速度（NFC）の向上が不可欠であり、次世代カードの配布を待つ必要がある。


## 5. 推奨ロードマップとリスク緩和策

本検証結果および技術動向に基づき、Tobariプロジェクトでは以下の3段階のロードマップを推奨する。また、万が一想定よりも早く量子超越（CRQCの実現）が到来した場合のリスク緩和策（Contingency Plan）についても定義する。

### 5.1. 段階的導入ロードマップ

| フェーズ | 時期（目安） | Web / Viewer | Mobile / Passkey | IC Card | 戦略の要点 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Phase 1**<br/>(Issuer-First) | **現在<br/>〜2026** | **Hybrid実装**<br/>(WASMにより今すぐ対応) | **P-256 (現状維持)**<br/>※PQC署名によるログ保全で補強 | **AES/SHA (共通鍵)**<br/>※Issuer署名のみML-DSA化 | **「発行者の真正性」を最優先でPQC化**。<br/>個人のデバイス認証は既存技術を用いるが、その認証履歴を行政側でPQC署名しアーカイブすることで、間接的に真正性を担保する。 |
| **Phase 2**<br/>(Hybrid) | **2027<br/>〜2030** | **Native API化**<br/>(ブラウザ標準機能へ移行) | **Hybrid対応開始**<br/>(対応機種から順次ML-DSAへ) | **Issuer署名運用定着**<br/>※次世代カード規格策定 | **「異機種混在」の許容**。<br/>PQC対応デバイスを持つユーザーには完全なPQC検証を提供し、そうでないユーザーにはPhase 1の補強策を継続する。 |
| **Phase 3**<br/>(Full PQC) | **2030年代<br/>後半〜** | **Legacy廃止**<br/>(PQC Only運用) | **PQC Native**<br/>(P-256廃止) | **次世代カード普及**<br/>(チップ内PQC演算) | **「古典暗号の完全排除」**。<br/>市場のデバイスがほぼ一巡した段階で、レガシー暗号のサポートを終了する。 |

### 5.2. 「203x年 量子超越」シナリオへの対応 (Contingency Plan)

仮にロードマップの途中（Phase 2等）で、突発的な技術ブレークスルーによりCRQC（暗号解読可能な量子コンピュータ）が実現した場合でも、本アーキテクチャは致命的な破綻を防ぐ多層防御を備えている。

#### (1) 「今」盗聴されても、未来でも読まれない (Confidentiality)
本PoCで採用した **Hybrid HPKE (P-256 + ML-KEM)** 暗号化により、仮に203x年にP-256が破られたとしても、同時にML-KEM（格子暗号）が破られない限り、**現在(2026年)に保存・通信されたデータを復号することはできない**。これにより、「Harvest Now, Decrypt Later（今盗んで後で解読）」攻撃を無効化している。

#### (2) 発行者署名の永続性 (Issuer Authenticity)
発行者署名は **Hybrid Signature (P-384 + ML-DSA)** であるため、古典暗号が破られてもML-DSAが健在であれば、証明書の偽造は不可能である。これにより、**「いつ発行された証明書か」という社会的信頼の根幹は揺るがない**。

#### (3) ユーザー認証の緊急措置 (Device Binding Fallback)
もっとも脆弱性が懸念されるのは、ユーザーのデバイス鍵（Passkey P-256）である。これが破られた場合、なりすましのリスクが生じる。これに対しては以下の緊急措置を発動する。

*   **Offline Verificationの停止**: P-256署名を用いたオフライン検証を無効化し、強制的にオンライン検証（サーバーサイドでの多要素認証や、共通鍵認証）へ誘導する。
*   **PQC署名済みログの活用**: 過去の署名データについては、**「発行時点ではその鍵が有効であった」ことを行政側がPQC署名したログ（Timestamping）** と照合することで、事後的な否認防止を担保する。



## 6. 結論

検証の結果、PQC導入によるオーバーヘッドは、ファイルサイズで数十KB、処理時間で数ミリ秒の範囲に収まることが確認された。
特に「自己完結型ビューアー」モデルにおいては、ベースとなるWASMやフォントのサイズが支配的であるため、PQCによる相対的なサイズ増加は限定的である。

また、ユーザーデバイス（Passkey）のPQC対応には時間を要するものの、発行者（Issuer）側の署名を先行してPQC化（ハイブリッド化）することには十分な意義がある。これにより、**「証明書自体の真正性（誰が発行したか）」については直ちに耐量子安全性を確保しつつ、デバイス認証についてはハードウェアの進化に合わせて段階的に強度を上げていく** という、現実的かつ切れ目のない移行が可能となる。

したがって、**「住民票の電子交付」のような長期的な真正性が求められる公的証明書において、現在からPQCハイブリッド構成を導入することは技術的に十分可能であり、かつ将来的なリスクヘッジとして推奨される** と結論付ける。
