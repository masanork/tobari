# FATF「アンホステッド・ウォレット」規制要件とSCACの適合性分析

**Date:** 2026-01-09
**Project:** JAOPP (Japan Open Privacy Platform) / Tobari
**Subject:** Self-Hosted Crypto Account Ownership Credential (SCAC)

---

## 1. 背景：FATFにおけるアンホステッド・ウォレットの議論

FATF（金融活動作業部会）は、2021年10月に改訂された「暗号資産及び暗号資産交換業者（VASP）のリスクベース・アプローチに関するガイダンス」において、**アンホステッド・ウォレット（Unhosted Wallet / 自己管理型ウォレット）** との取引に関するリスクと対応策を明確化しました。

### 1.1 主な要件と課題
VASPがアンホステッド・ウォレットと取引（送金・受取）を行う際、以下の対応が求められます（トラベルルール等の拡張）。

1.  **所有者の識別 (Identification):** アンホステッド・ウォレットの背後にいる自然人または法人が誰であるかを知る必要がある。
2.  **実在性の検証 (Verification):** 申告された身元情報が正確であることを、信頼できる独立した情報源（公的証明書等）で確認する必要がある。
3.  **管理権限の証明 (Proof of Ownership/Control):** その顧客が実際にそのウォレットアドレスの秘密鍵を管理している（＝サンクション対象者のウォレットに勝手に送金しているわけではない）ことを確認する必要がある。
4.  **プライバシーとの両立:** これらの情報を収集・保存する際、GDPR等のデータ保護規制を遵守する必要がある。

### 1.2 業界のジレンマ
従来の手法（スクリーンショットの提出や、少額送金テスト＝Satoshi Test）は、UXが悪く、偽造も容易であり、かつ過剰な個人情報をVASPに渡すことになるため、プライバシーリスクが高いという問題がありました。

---

## 2. SCAC (本PoC) の適合性分析

今回試作した **SCAC (Self-Hosted Crypto Account Ownership Credential)** は、これらの課題に対して「mDoc (ISO 18013-5)」と「ZKP (Zero-Knowledge Proof)」を用いて解決を図るものです。

### 2.1 要件対照表

| FATF要件 / 課題 | SCACのアプローチ | 評価 |
| :--- | :--- | :--- |
| **1. 所有者の識別** | パスポート/JPKIから読み取った氏名・生年月日等の正確な属性情報をクレデンシャル(`io.github.masanork.tobari.person`)に格納。 | ✅ **適合**<br>偽名やタイプミスを排除可能。 |
| **2. 実在性の検証** | ICチップ内の政府署名データ（SOD/署名用電子証明書）を暗号学的に検証した上で発行されるため、物理的な身分証提示と同等以上の信頼性を持つ。 | ✅ **適合 (高信頼)**<br>Passive Authにより偽造パスポートを検知可能。 |
| **3. 管理権限の証明** | 発行フローにおいて、ウォレットによる電子署名（Challenge-Response）を必須としている。証明書内に紐付いたアドレス(`accounts`)が明記される。 | ✅ **適合**<br>「私のID」と「私のウォレット」の結合が保証される。 |
| **4. サンクション選別** | 証明書内の氏名・生年月日を用いることで、VASP側でOFACリスト等との照合（スクリーニング）が自動化可能。 | ✅ **適合**<br>自動化によりコンプライアンスコストを削減。 |
| **5. プライバシー** | **ZKP (Zero-Knowledge Proof)** により、パスポート番号等の不要な識別子を隠蔽しつつ、真正性を証明。Selective Disclosureにより必要な属性のみを開示可能。 | 🚀 **優位性あり**<br>FATF要件を満たしつつ、データ最小化の原則を遵守。 |

## 3. 詳細分析

### 3.1 「信頼の起点」の確立
SCACは、**パスポート (ICAO 9303)** や **マイナンバーカード (JPKI)** という、国家が発行した最高レベルの身分証（IAL3相当）を「信頼の起点（Root of Trust）」としています。
単にOCRで画像を読み取るだけでなく、NFC経由でICチップ内の電子署名を検証する（Passive Authentication）実装となっているため、「精巧なコピー」によるなりすましを排除できます。これはFATFが求める「信頼できる独立した情報源」の要件を高い水準で満たします。

### 3.2 ウォレット所有の証明 (Address Binding)
SCACのデータ構造には、本人情報と同時に `accounts` 配列が含まれています。この配列に含まれるアドレスは、発行時に秘密鍵による署名検証に成功したものに限られます。
これにより、このクレデンシャルを提示されたVASPは、**「この実在する個人（A氏）が、確実にこのアドレス（0x...）を管理している」** ことを、再度の署名要求なしに（または提示時の署名とセットで）即座に確認できます。

### 3.3 マルチチェーン対応とUX
FATF対応の現場では、ユーザーが複数のチェーン（Ethereum, Solana, Polygon...）を利用する場合、それぞれで所有証明を求められる煩雑さがありました。
SCACの「ポートフォリオ」構造は、一度のKYCで全チェーンのアドレスを一括して証明できるため、ユーザー体験を損なわずにコンプライアンスレベルを向上させることができます。

### 3.4 ZKPによる「トラッキング防止」
パスポート番号を含めない設計（ZKPによるSOD検証証明）は、Web3特有の課題への回答です。
ブロックチェーン上のトランザクションは永続的に公開されるため、そこに紐付く検証データにパスポート番号が含まれていると、将来的に暗号技術が破られた際に個人の移動履歴や国籍が全て露見するリスクがあります。
SCACのアプローチ（番号は捨てて、検証事実のProofのみを残す）は、この「オンチェーン・プライバシー」のリスクを最小化する設計となっています。

## 4. 残された課題と今後の検討事項

### 4.1 発行者（Issuer）の信頼性 (Trust Framework)
技術的に検証可能でも、法的に有効かという問題があります。
*   **現状:** 自己署名、または未認可の「Tobari Wallet」が発行。
*   **課題:** VASPが「Tobariの発行した証明書」を信頼してよいか？
*   **解決策:** Tobari（発行者）自体がトラストフレームワーク（OpenID Federationなど）に参加するか、あるいは政府・自治体・認可KYC業者がIssuerとなるモデルへの移行。または、**「ユーザー自身のデバイスで発行し、VASPがその場でZK検証する（Self-Attested but Verifiable）」** モデルの確立。

### 4.2 失効管理 (Revocation)
パスポートの紛失や有効期限切れ、あるいはウォレットの秘密鍵流出に対応する必要があります。
*   **mDoc:** 有効期限(`expiry_date`)はあるが、リアルタイムの失効リスト(CRL/OCSP)の仕組みが必要。
*   **解決策:** mDocの `status` 機構の実装や、Short-lived credentials（短期間のみ有効な証明書）の運用。

### 4.3 P2P取引への適用
FATFは現在、P2P取引（Unhosted同士）の規制には慎重ですが、将来的には議論が進む可能性があります。SCACはP2Pでお互いの信頼性を確認するツールとしても機能しますが、その際のプライバシー基準（相手にどこまで名前を見せるか）は、ユーザーインターフェース側での制御が重要になります。

---

## 5. 結論

本PoC (SCAC) は、FATFがVASPに求める「アンホステッド・ウォレットに係るデューデリジェンス」の要件を、**技術的に高い水準（ICチップ検証・署名結合）** で満たしています。

特に、**ZKPを用いたパスポート番号の秘匿**は、コンプライアンス（本人確認）とプライバシー（データ保護）という、しばしば対立する要件を両立させるための鍵となる技術であり、次世代の本人確認基盤として有望なモデルケースであると評価できます。
