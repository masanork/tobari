# **マイナンバーカード（個人番号カード）の技術仕様およびAPDUコマンド構造に関する包括的調査報告書**

## **1\. エグゼクティブサマリー**

本報告書は、日本におけるデジタルアイデンティティの中核を担う「個人番号カード（マイナンバーカード）」の技術的仕様、特に公的個人認証サービス（JPKI）および券面事項入力補助アプリケーション（Card-AP）との通信プロトコルについて、極めて詳細かつ網羅的な分析を行ったものである。本調査は、ISO/IEC 7816およびISO/IEC 14443規格に基づくスマートカード技術の基礎から、マイナンバーカード独自のAPDU（Application Protocol Data Unit）コマンド体系、暗号化処理フロー、そして実際のリーダーアプリケーション開発における実装詳細に至るまでをカバーする。

調査の手法として、公開されているJ-LIS（地方公共団体情報システム機構）の仕様書に加え、jpki/myna、TRETJapanNFCReader、OpenSCといった主要なオープンソースプロジェクトのソースコードおよびコミュニティでの議論（Issue/Discussion）を詳細に分析し、公式ドキュメントでは明文化されていない実装上の挙動や「暗黙知」となっている技術的制約を明らかにした。

本報告書の目的は、PC/SC規格を用いたデスクトップアプリケーションや、CoreNFC（iOS）/ Android NFC APIを用いたモバイルアプリケーションを「スクラッチ（ゼロベース）」で開発しようとする技術者に対し、認証、電子署名、基本4情報（氏名・住所・生年月日・性別）、および顔写真データへのアクセスを実現するための完全な技術的指針を提供することにある。特に、独自仕様であるCOMPUTE DIGITAL SIGNATUREコマンドのパラメータ設定や、ASN.1（Abstract Syntax Notation One）形式で格納されたデータのデコーディング、さらには複数のアプリケーションID（AID）を跨ぐセッション管理の複雑性について深く掘り下げる。

## **2\. 序論：日本のデジタルID基盤とマイナンバーカード**

### **2.1 背景と位置づけ**

マイナンバーカードは、日本の行政手続きのデジタル化および本人確認の厳格化を目的として導入されたICカードである。このカードは、単なるプラスチックカードではなく、高度な暗号演算能力を持つICチップ（Secure Element）を搭載したコンピュータであり、その内部には「公的個人認証サービス（JPKI）」に基づく電子証明書が格納されている。

開発者にとって重要なのは、このカードが「ハイブリッドカード」であるという点である。接触型インターフェース（ISO/IEC 7816）と非接触型インターフェース（ISO/IEC 14443 Type B）の両方を備えており、物理的な接触リーダーだけでなく、NFC搭載スマートフォンを通じたアクセスが可能となっている。この二重性が、利用シーンを拡大させる一方で、リーダー側の実装における物理層のハンドリング（特にType B変調の扱い）に特有の要件を課している。

### **2.2 システムアーキテクチャの概要**

マイナンバーカードの内部OSは、マルチアプリケーション対応のプラットフォーム（GlobalPlatform準拠または類似の独自OS）上で動作しており、単一の機能ではなく、独立した複数の「アプリケーション」が共存している。開発者が意識すべき主要なアプリケーションは以下の2つである。

1. JPKIアプリケーション（JPKI-AP）:  
   デジタル署名および利用者証明を行うためのコアアプリケーション。秘密鍵による暗号演算機能を提供する。  
2. 券面事項入力補助アプリケーション（Card-AP / Input Assistance AP）:  
   カード表面に記載されている個人情報（基本4情報）や顔写真データを、デジタルデータとして読み出すためのアプリケーション。

これらのアプリケーションは、それぞれ異なる権限管理（PINの種類）とファイルシステム構造を持っており、開発者はAPDUコマンドを用いてこれらを明示的に切り替えながら対話を行う必要がある。

**3\. 物理層およびデータリンク層の通信仕様**

リーダーアプリケーションをスクラッチで構築する場合、最初に取り組むべき課題は、ICカードとの物理的な接続確立である。ここでは、特にモバイルデバイスや組み込みリーダーで重要となる非接触通信（NFC）の仕様について詳述する。

### **3.1 ISO/IEC 14443 Type Bの採用とその影響**

日本の交通系ICカード（Suica、PASMO等）がFeliCa（ISO/IEC 18092 / Type F）を採用しているのに対し、マイナンバーカード（および運転免許証、パスポート）は**ISO/IEC 14443 Type B**を採用している。これは世界的な身分証規格（ICAO 9303）との親和性を考慮したものであるが、国内の一般的なNFCリーダー実装において技術的な落とし穴となることが多い。

Type Bの特徴は、Type A（MIFARE等）と比較して変調度（Modulation Index）が浅く（10% ASK）、物理的な通信の安定性を確保するためにリーダー側のアンテナ調整やポーリング設定がシビアになる点にある。

#### **ポーリングと衝突防止（Anti-Collision）**

リーダーは定期的にポーリングコマンド（REQB または WUPB）を送出し、フィールド内のカードを探索する。マイナンバーカードはこれに対し、ATQB（Answer To Request Type B）を返送する。  
ATQBには、プロトコル情報やUID（PUPI: Pseudo-Unique PICC Identifier）が含まれる。ここで重要なのは、マイナンバーカードのPUPIはランダムIDである可能性が高く、カードの永続的な識別子として利用すべきではないという点である。セッションごとの一時的なIDとして扱う設計が求められる。

### **3.2 データリンク層：ISO-DEP (ISO 14443-4)**

物理的な接続が確立されると、通信は**ISO-DEP**（ISO 14443-4 Data Exchange Protocol）層へと移行する。この層は、上位のAPDUコマンドを分割・結合し、エラー訂正を行う役割を担う。

* **ブロック伝送プロトコル**: 通信は「ブロック」単位で行われる。  
  * **I-Block (Information Block)**: アプリケーションデータ（APDU）を運ぶ。  
  * **R-Block (Receive Ready Block)**: ACK/NACK制御を行う。  
  * **S-Block (Supervisory Block)**: 待ち時間延長（WTX）などの制御を行う。

特にマイナンバーカードでの暗号演算（署名生成など）は数秒を要する場合があり、カードから送られてくるS-Block (WTX: Waiting Time Extension)要求に対して、リーダー側が適切に応答しなければタイムアウトエラーが発生する。高レベルAPI（CoreNFCやAndroid IsoDep）を使用する場合、このハンドリングはOSが代行するが、PC/SCドライバや組み込みマイコンで実装する場合は、WTX応答の実装が必須となる。

## ---

**4\. アプリケーション層：APDUコマンド構造とセッション確立**

ここからは、論理的な通信プロトコルであるAPDU（Application Protocol Data Unit）の詳細に入る。ISO/IEC 7816-4で規定されたこの構造は、カードに対する命令（Command APDU）と応答（Response APDU）のペアで構成される。

### **4.1 APDUの基本構造**

マイナンバーカードに対する全ての操作は、以下の形式のバイト列を送信することで行われる。

| フィールド | 長さ (Byte) | 説明 |
| :---- | :---- | :---- |
| **CLA** | 1 | クラスバイト。標準命令は 00、独自拡張は 80 が多用される。 |
| **INS** | 1 | 命令コード（Instruction）。A4（Select）、B0（Read Binary）、20（Verify）など。 |
| **P1** | 1 | パラメータ1。コマンドごとの詳細設定。 |
| **P2** | 1 | パラメータ2。コマンドごとの詳細設定。 |
| **Lc** | 0 or 1 or 3 | データフィールドの長さ（送信データのバイト数）。 |
| **Data** | Lc | コマンド本体のデータ（PIN番号や書き込むデータなど）。 |
| **Le** | 0 or 1 or 3 | 期待するレスポンスの最大長。00 は最大長（256バイトまたは拡張）を意味する。 |

拡張APDU（Extended APDU）への対応:  
マイナンバーカードの電子証明書は数キロバイトに及ぶため、256バイトを超えるデータを一度に送受信できる「拡張APDU」の使用が望ましい。しかし、リーダーやOSの制限により拡張APDUが使えない場合は、READ BINARYコマンドにおいてオフセット（P1, P2）をずらしながら分割して読み出す実装が必要となる。

### **4.2 アプリケーション選択 (SELECT FILE) とAID**

カードとの通信セッションは、必ず「どのアプリケーションと話すか」を指定するSELECT FILEコマンドから始まる。これを怠ると、コマンドはルートディレクトリ（MF）に対して発行されるか、エラーとなる。

マイナンバーカードには、J-LIS（地方公共団体情報システム機構）に割り当てられたRID（Registered Application Provider Identifier）を含む独自のAID（Application Identifier）が設定されている。

#### **表1: マイナンバーカードにおける主要なAID一覧**

| AID (Hex) | 名称 | 用途・解説 |
| :---- | :---- | :---- |
| D3 92 F0 00 26 01 00 00 00 01 | **JPKI-AP** | **公的個人認証用AP**。 電子署名、利用者証明書の取得に使用。最も重要。 |
| D3 92 10 00 31 00 01 01 04 08 | **Card-AP** | **券面事項入力補助AP**。 基本4情報、顔写真、マイナンバー（個人番号）の取得に使用。 |
| D3 92 10 00 31 00 01 01 01 00 | Expansion AP | 拡張領域AP。独自サービスの格納用（通常は空き領域）。 |
| D3 92 10 00 31 00 01 01 04 01 | Pin Status AP | PINステータス確認用AP（一部実装で使用）。 |

実装上の重要ポイント（iOS開発者向け）:  
iOSのCoreNFCを使用する場合、アプリの Info.plist 内にある com.apple.developer.nfc.readersession.iso7816.select-identifiers キーに、上記のAIDを全てリストアップしておく必要がある。これを怠ると、OSのNFC探索機能がマイナンバーカードを「非対応タグ」としてフィルタリングしてしまい、検出イベントすら発生しない事態に陥る。特に、TRETJapanNFCReader などのオープンソースライブラリでは、これら全てのAIDが定義されていることが確認できる1。

#### **SELECT FILE コマンドの詳細**

アプリケーションを選択するためのコマンドは以下の通りである。

* **CLA**: 00  
* **INS**: A4  
* **P1**: 04 (Select by DF Name / AID)  
* **P2**: 0C (File Control Informationを返さない) または 00  
* **Lc**: AIDの長さ（通常 0A \= 10バイト）  
* **Data**: 上記のAID

例：JPKI-APを選択する場合  
00 A4 04 0C 0A D3 92 F0 00 26 01 00 00 00 01  
正常に選択されると、カードはステータスワード 90 00 を返す。

**5\. JPKIアプリケーション詳解：公的個人認証**

JPKI-APは、マイナンバーカードのセキュリティの中核である。ここでは、電子証明書の読み出しから、秘密鍵を用いた電子署名の生成までのプロセスを詳述する。

### **5.1 ファイルシステムマップ (JPKI)**

JPKI-APを選択した後、その配下にあるEF（Elementary File）にアクセスするには、2バイトのFile IDを使用する。

#### **表2: JPKI-AP内の主要EF一覧**

| File ID | 名称 | アクセス条件 | 内容詳解 |
| :---- | :---- | :---- | :---- |
| 00 18 | **Auth PIN IEF** | なし | **利用者証明用PIN（4桁）** の検証先ファイル。 |
| 00 1B | **Sign PIN IEF** | なし | **署名用パスワード（6-16桁）** の検証先ファイル。 |
| 00 0A | **Auth Certificate** | 誰でも読取可 | **利用者証明用電子証明書**（X.509）。ログイン等の認証に使用。 |
| 00 01 | **Sign Certificate** | 誰でも読取可 | **署名用電子証明書**（X.509）。e-Tax等の文書署名に使用。 |
| 00 1A | **Auth Private Key** | Auth PIN検証後 | 利用者証明用秘密鍵への論理参照。 |
| 00 17 | **Sign Private Key** | Sign PIN検証後 | 署名用秘密鍵への論理参照。 |

### **5.2 PIN検証プロセス (VERIFY)**

マイナンバーカードの操作において最もトラブルが多いのがPIN検証である。JPKIには2種類のPINが存在し、それぞれ異なるファイル（IEF）に対して検証を行う必要がある。

1. **利用者証明用暗証番号（4桁の数字）**:  
   * 対象ファイル: 00 18  
   * リトライ許容回数: **3回**（連続して間違えるとロックされる）  
2. **署名用パスワード（6〜16桁の英数字）**:  
   * 対象ファイル: 00 1B  
   * リトライ許容回数: **5回**（連続して間違えるとロックされる）

VERIFYコマンドの構造:  
通常のISO 7816標準とは異なり、マイナンバーカードでは P2 パラメータに特殊な値 80 を使用する場合があることが、オープンソース実装の解析から明らかになっている2。

* **CLA**: 00  
* **INS**: 20  
* **P1**: 00  
* **P2**: 80 (ここが重要)  
* **Lc**: PINのバイト長  
* **Data**: PINのASCIIコード列

**手順:**

1. JPKI-APを選択。  
2. 検証したいPINのIEFを選択（SELECT FILE）。  
   * 例：4桁PINなら 00 A4 02 0C 02 00 18  
3. VERIFYコマンドを送信。  
   * 例：PIN "1234" の場合 \-\> 00 20 00 80 04 31 32 33 34

**レスポンス解析:**

* 90 00: 成功。セキュリティ状態が解除され、秘密鍵へのアクセスが可能になる。  
* 63 C2: 失敗。**残り2回**。  
* 63 C1: 失敗。**残り1回**（警告が必要）。  
* 63 C0: **ロック発生**。市区町村窓口での初期化が必要となるため、アプリケーション側では 63 C1 が返ってきた時点でユーザーに強い警告を出すか、処理を中断する安全策の実装が推奨される。

### **5.3 電子証明書の読み出し (READ BINARY)**

証明書（EF 00 0A や 00 01）はアクセス制御がかかっておらず、PINなしで読み出しが可能である。しかし、データサイズが大きいため（通常1KB〜2KB）、読み出しには工夫が必要である。

**手順:**

1. 証明書EFを選択（例: 00 A4 02 0C 02 00 0A）。  
2. READ BINARYコマンドでデータを取得。

**READ BINARYコマンド:**

* **CLA**: 00  
* **INS**: B0  
* **P1**: オフセットの上位バイト  
* **P2**: オフセットの下位バイト  
* **Le**: 読み出す長さ（00 指定で最大長）

拡張APDU非対応の環境では、ループ処理が必要となる。

1. P1=00, P2=00, Le=00 (256バイト読み出し)  
2. P1=01, P2=00, Le=00 (次の256バイト読み出し)...  
   というようにオフセットを加算しながら、ステータスワード 6B 00（パラメータ不正＝オフセット範囲外）やデータ長が不足するまで繰り返す。

取得されるデータは、DER（Distinguished Encoding Rules）エンコードされたX.509証明書そのものである。ただし、一部の実装では先頭に独自のヘッダが付与される場合があるため、ASN.1解析ライブラリに渡す前に、先頭バイトが 30 82 （SEQUENCEタグ \+ 長さ）で始まっているか確認し、必要ならパディングを除去する処理を入れると堅牢である3。

### **5.4 電子署名の生成 (COMPUTE DIGITAL SIGNATURE)**

これこそがリーダーアプリケーション開発における最大の難所である。この機能は、カード外部から送信されたデータのハッシュ値に対し、カード内部の秘密鍵で署名を施し、その結果を返すものである。秘密鍵はカード外部には一切出ないため、非常に高いセキュリティが担保される。

重要：コマンドクラスバイトの独自性  
標準的なISOコマンドのCLAは 00 であるが、マイナンバーカードの暗号演算コマンドでは、プロプライエタリ（独自拡張）を示す 80 が使用される。これを 00 で送信すると 6D 00（Instruction Not Supported）エラーとなる4。  
**署名生成フロー:**

1. **JPKI-AP選択**: Select JPKI  
2. **PIN IEF選択**: Select EF (00 1B)  
3. **PIN検証**: Verify (Password)  
4. **秘密鍵EF選択**: Select EF (00 17\) (署名用秘密鍵)  
5. **署名実行**: COMPUTE DIGITAL SIGNATURE

**COMPUTE DIGITAL SIGNATURE コマンド構造:**

* **CLA**: **80**  
* **INS**: **2A**  
* **P1**: 00  
* **P2**: **80** (独自パラメータ)  
* **Lc**: データ長  
* **Data**: **DigestInfo構造体** (下記参照)  
* **Le**: 00 (または期待される署名長、RSA2048bitなら256バイト)

署名対象データ (DigestInfo) の構築:  
カードに送信するデータは、署名したい文書そのものではなく、その「ハッシュ値」をASN.1構造体である DigestInfo に格納したものである。カード側はハッシュアルゴリズム（SHA-256など）を知る必要がないため、この形式で渡すのがPKCS\#1の標準である。  
SHA-256を使用する場合のデータ構造（DERエンコード済バイト列）:

30 31 (SEQUENCE, 49 bytes)  
   30 0D (SEQUENCE, 13 bytes)  
      06 09 (OBJECT IDENTIFIER, 9 bytes)  
         60 86 48 01 65 03 04 02 01 (id-sha256 OID)  
      05 00 (NULL)  
   04 20 (OCTET STRING, 32 bytes)  
      \[32バイトのハッシュ値\]

開発者は、対象データのSHA-256ハッシュを計算し、上記のヘッダ（30 31... 04 20）を付与したバイト列をAPDUのDataフィールドに設定して送信する5。

レスポンス:  
成功すると、256バイト（2048bit鍵の場合）の署名データ \+ 90 00 が返る。このデータは生のRSA署名値であり、これを利用してCMS（Cryptographic Message Syntax）やXML署名などの上位フォーマットを構築するのはアプリケーション側の責務である。

**6\. 券面事項入力補助AP詳解：基本4情報と顔写真**

JPKIが「オンラインでの本人確認」用であるのに対し、Card-AP（券面事項入力補助AP）は「対面またはオフラインでのデータ入力補助」を目的としている。ここには、カード券面に記載されている情報がデジタルデータとして格納されている。

### **6.1 セキュリティモデルの違い**

Card-APの最大の特徴は、**アクセスに「利用者証明用PIN（4桁）」を使用する**点である。JPKIの署名用パスワードではない。このため、ユーザーは4桁の暗証番号を入力するだけで、住所や氏名、そして顔写真データをアプリに取り込むことができる。

### **6.2 ファイルシステムマップ (Card-AP)**

**AID**: D3 92 10 00 31 00 01 01 04 08

#### **表3: Card-AP内の主要EF一覧**

| EF ID | 内容 | データ形式 | 備考 |
| :---- | :---- | :---- | :---- |
| 00 11 | **Card-AP用 PIN IEF** | \- | 4桁PINの検証先（JPKIの 00 18 とは論理的に別だが、値は同期している運用が多い）。 |
| 00 01 | **基本4情報** | ASN.1 | 氏名、住所、生年月日、性別。 |
| 00 02 | **顔写真** | ASN.1 (wrap) | JPEG/JPEG2000データ。 |
| 00 03 | **マイナンバー（個人番号）** | ASN.1 | 12桁の番号。**アクセス制限が厳格**。 |

※注意：マイナンバー（EF 00 03）へのアクセスには、さらに上位の権限や特別なOCR処理を伴う認証が必要となる場合が多く、一般の民間アプリ開発では法的な利用制限（番号法）も含めてアクセスすべきではない領域である。本報告書では一般開発者が利用可能な基本4情報と顔写真に焦点を当てる。

### **6.3 データ取得フロー**

1. **Card-AP選択**: 00 A4 04 0C 0A D3 92 10 00 31 00 01 01 04 08  
2. **PIN IEF選択**: 00 A4 02 0C 02 00 11  
3. **PIN検証**: 00 20 00 80 04 \[PIN\] (4桁)  
4. **データEF選択**:  
   * 基本4情報: 00 A4 02 0C 02 00 01  
   * 顔写真: 00 A4 02 0C 02 00 02  
5. **データ読み出し**: READ BINARY (分割読み出し推奨)

### **6.4 データのデコーディング (ASN.1解析)**

取得したデータはバイナリ形式のASN.1構造体であるため、これをパースして意味のある値を取り出す必要がある。

**基本4情報 (EF 00 01\) の構造概略:**

コード スニペット

Sequence {  
   header: \[独自タグ\],  
   name: UTF8String (氏名),  
   address: UTF8String (住所),  
   dob: NumericString (生年月日 YYYYMMDD),  
   sex: NumericString (性別コード 1=男, 2=女...),  
  ...  
}

それぞれの要素はTLV（Tag-Length-Value）形式でエンコードされている。具体的なタグ番号はJ-LIS仕様書に依存するが、オープンソースのパーサ（TRETJapanNFCReaderのパーサクラス等）を参照することで、各フィールドのタグ特定が可能である。特に文字コードはUTF-8が採用されているが、外字等の扱いで稀に特殊なエンコーディングが含まれる可能性がある点に留意する。

顔写真データ (EF 00 02\) の構造:  
顔写真ファイルから読み出したデータもASN.1でラップされている。  
Tag (Octet String) \+ Length \+ Value (Image Data)  
画像の実体は、このValue部分に含まれる。バイナリデータの先頭数バイトを確認し、FF 4F (JPEG2000 Codestream) や FF D8 (JPEG) などのマジックナンバーを探すことで、ASN.1ヘッダを除去する位置を特定できる。マイナンバーカードの顔写真は一般的に高圧縮なJPEG2000形式が採用されているケースが多いため、アプリ側でJPEG2000のデコードライブラリが必要になる場合がある6。

**7\. 実装ガイド：オープンソースからの知見と注意点**

### **7.1 オープンソースプロジェクトの分析**

#### **jpki/myna (C言語/Linux系)**

このプロジェクトは、低レベルなAPDU通信を隠蔽し、高レベルなAPIを提供するライブラリである。

* **知見**: sc-explorer などのツールを含んでおり、未知のカード仕様を解析する際のコマンドラインユーティリティとして有用である。特に jpki\_sign 関数内部の実装において、DigestInfoのパディング処理が詳細に記述されており、自前実装の際のリファレンスとなる7。

#### **TRETJapanNFCReader (Swift/iOS)**

iOS向けの主要なライブラリ。

* **知見**: 複数のAIDを包括的に定義し、セッション切断を防ぐ設計になっている。また、読み出したデータの日本語文字コード変換（Shift-JISとUTF-8の混在など）に関する実用的な処理が含まれている。顔写真データの抽出ロジックも参考になる1。

#### **OpenSC (汎用スマートカードドライバ)**

* **課題**: Windows環境において、OS標準のスマートカードフレームワーク（Minidriver）が、マイナンバーカードの「署名用証明書」を認識しないという問題が報告されている3。  
* **原因と対策**: これは、署名用鍵へのアクセス時に「ユーザーの同意（User Consent）」、すなわち明示的なPIN入力をドライバが要求する仕様に対し、Windows側が適切にUIを出さないことに起因する。スクラッチ開発する場合、WindowsのCSP/KSPに依存せず、WinSCard APIを用いて直接APDUを送信する（Passthroughモード）ことで、このOS側の不具合を回避し、確実にPIN認証と署名を行うことができる。

### **7.2 プラットフォーム固有の実装要件**

**iOS (CoreNFC)**:

* NFCTagReaderSession を使用する。pollingOption には .iso14443 を指定する。  
* tagReaderSession:didDetectTags: 内で case.iso7816 としてタグを認識した後、connect する。  
* Info.plistへのAID記述は必須である。これがないと、どれだけコードが正しくても物理層で通信が遮断される。

**Android (Android.nfc.tech.IsoDep)**:

* IsoDep.get(tag) でインスタンスを取得。  
* setTimeout を長めに設定すること（最低でも3000ms〜5000ms）。署名生成（RSA演算）はチップの性能によっては数秒かかるため、デフォルトのタイムアウトでは失敗するリスクがある。  
* transceive メソッドでAPDUを送受信する。拡張APDUのサポート状況を isExtendedLengthApduSupported() で確認し、非対応機種の場合は分割送受信ロジックに切り替える分岐が必要である。

**8\. 結論**

マイナンバーカードのリーダーアプリケーション開発は、標準技術（ISO 7816/14443）と日本独自の仕様（J-LIS仕様、独自APDU）が複雑に絡み合う領域である。本調査で明らかになった主要な成功要因は以下の3点に集約される。

1. **正確なAID管理**: JPKI-APとCard-APの役割を明確に区別し、適切なタイミングで SELECT FILE を発行してコンテキストを切り替えること。  
2. **独自APDUの理解**: 特に電子署名における 80 2A コマンドや、PIN検証における P2=80 といった、標準仕様からの逸脱点を正確に実装すること。  
3. **データ構造の把握**: ASN.1 DER形式のデコーディングロジック（特にDigestInfoの構築と、属性情報のパース）を正しく実装すること。

本報告書に記載されたAPDUシーケンスとデータ構造に従うことで、開発者はブラックボックス化されたドライバに依存することなく、堅牢かつ柔軟なマイナンバーカード対応アプリケーションを構築することが可能となる。今後の展望として、スマートフォンへのJPKI機能搭載（スマホ用電子証明書）が進んでいるが、その場合も論理的なAPDU構造（GP-SE上のアプレット）は本報告書の内容と高い互換性を持つことが予想され、ここで得られた知見は長期的に有効であると考えられる。
